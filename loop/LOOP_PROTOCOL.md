# Loop 协议

## 1. 目的

本协议把一次工程活动定义为有状态、有证据、有边界的循环，而不是反复提示。每轮只推进一个主要工作项，并始终保留可恢复状态。

## 2. Loop 规格六要素

| 要素 | 本项目定义 |
|---|---|
| Trigger | 当前默认为人工触发；未来可由 CI 失败、已批准工作项或定时维护触发 |
| Goal | 迁移为 PySide6 桌面工作台，同时保持科学计算、网络降级、可解释性和交付合同 |
| Verification | 需求追溯 + 自动门禁 + 独立审查 + 必要的 Windows 真机证据 |
| Stop rule | 达到命名终态、需要人类决策、无安全进展、或门禁连续失败时停止 |
| Memory | `state/`、`registers/`、`evidence/`、ADR 和工作项 |
| Authority | 仅执行已授权范围；发布、依赖许可接受和不可逆动作需要人类门禁 |

## 3. 单轮状态机

```text
OBSERVE -> SPECIFY -> DECIDE -> PLAN -> IMPLEMENT
    -> VERIFY -> REVIEW -> LEARN -> ADVANCE
                    |                    |
                    +---- RECOVER <-----+
```

### OBSERVE

输入：`state/current.json`、活动工作项、最新门禁、工作树、风险。

输出：已确认的当前事实和待解决差距。

退出条件：不得依赖记忆猜测当前状态；关键事实已有直接证据。

### SPECIFY

输入：相关 `REQ-*`、`AC-*`、架构与 ADR。

输出：单一、有边界、可验收的工作项；明确 scope-in/scope-out。

退出条件：验收条件可由测试、检查或人工证据验证。

### DECIDE

输入：至少两个可行方案及代价。

输出：采用方案、拒绝方案、迁移与回滚后果；重大事项写 ADR。

退出条件：不存在未经记录的重大架构选择。

### PLAN

输入：工作项、依赖、风险、验证命令。

输出：小步实施序列和失败恢复点。

退出条件：每一步都可回滚，不与用户未提交修改冲突。

### IMPLEMENT

输入：已批准规格。

输出：最小但完整的变更、对应测试和文档。

退出条件：不存在超范围改动；所有副作用被明确控制。

### VERIFY

输入：变更、验收条件、失败模式、质量门禁。

输出：可复现命令、退出码、报告、截图或人工检查记录。

退出条件：不得用实现者自述替代证据；失败必须如实记录。

### REVIEW

输入：需求、差异、证据、风险和回滚方案。

输出：accept / changes_requested / needs_human。

退出条件：验证者与实现者逻辑分离；高风险结论有人工门禁。

### LEARN

输入：成功、失败、返工和新发现。

输出：`progress.jsonl`、风险/假设/缺陷更新、下一轮更好的上下文。

退出条件：经验已写入持久状态，而非只留在对话中。

### ADVANCE

输入：审查结论和终止规则。

输出：进入下一工作项或命名终态。

退出条件：`state/current.json` 和 `STATUS.md` 一致。

### RECOVER

输入：任一阶段（OBSERVE..ADVANCE）失败或异常中止时的现场——具体失败步骤、错误/异常信息，以及 `state/current.json` 中最后一次成功持久化的状态。

输出：重新稳定、内部一致的安全状态，以及对失败原因的诊断（记录进 `state/progress.jsonl` 及相关风险/缺陷登记）。

退出条件：状态已恢复一致且循环从 OBSERVE 重新开始；若在授权范围内无法恢复到一致状态，则升级为 `loop.json` 定义的命名终态（如 `blocked_external`、`no_safe_progress` 或 `failed`），不得停留在不一致或未持久化的中间状态。

## 4. 验证阶梯

| 等级 | 证据 | 可用于何种声明 |
|---|---|---|
| V0 | 无证据/主观判断 | 只能记为假设 |
| V1 | 静态检查、文件存在 | 结构已创建 |
| V2 | 单元测试、schema、类型/格式门禁 | 局部合同成立 |
| V3 | 集成、故障注入、Qt offscreen | 子系统协同成立 |
| V4 | Windows 真机、打包 EXE、自检、性能/视觉矩阵 | 发布候选成立 |
| V5 | 独立复核 + 人工发布门禁 + 可追溯产物 | 可发布/已接受 |

不得用低等级证据支持高等级声明，例如不能用 Qt offscreen 测试证明 Windows 真机渲染无误。

## 5. 命名终态

- `success`：工作项目标与证据全部满足，可推进。
- `needs_human`：存在产品、许可、发布或不可逆决策。
- `changes_requested`：验证失败但仍可继续修复。
- `blocked_external`：外部服务/环境阻塞，已有替代检查仍不足。
- `no_safe_progress`：当前权限内无法继续且不能合理假设。
- `cancelled`：由用户或批准的计划取消。
- `superseded`：目标被新决策替代。
- `failed`：本轮异常终止且状态已安全持久化。

## 6. 停止规则

任一条件成立即停止自动推进并持久化状态：

1. 工作项达到 `success`。
2. 需要新增运行依赖、改变发布合同或接受许可证义务而尚未批准。
3. 需要删除/覆盖用户资产、推送、发布或生产操作。
4. 同一必需门禁连续三次失败且没有新的诊断进展。
5. 工作树出现无法解释的外部变更。
6. 规格和真实系统互相矛盾，合理假设会改变产品行为。
7. 证据不足以支持继续推进的状态跃迁。

## 7. 实现者与验证者

- 实现者负责满足规格、补测试、保留最小差异。
- 验证者从需求出发，主动寻找反例、遗漏、回归和证据缺口。
- 验证者不得只复述实现者的测试结果；至少复跑关键门禁或检查原始证据。
- 最终集成者负责解决冲突并完成逐项验收审计。

### 独立性的具体机制

"实现者与验证者逻辑分离"是可核查的具体动作，不是态度声明：

1. **谁可以充当验证者**：必须是（a）一个不携带实现过程上下文的全新会话/进程——只读取规格、代码差异与可复现命令本身，不读取实现者的推理草稿或"为什么这样做没问题"的自我论证；或（b）一个独立的 subagent/角色，其输入限定为 REQ/AC/差异/门禁命令，明确排除实现者对失败原因的解释。两种形式都不接受"同一上下文内换个身份自称验证者"。
2. **必须复跑的最低门禁集合**：验证者必须亲自重新执行 `README.md`"必跑控制面门禁"六项（`validate_loop`、`check_traceability`、`render_status --check`、`render_backlog --check`、`check_core_boundaries`、`unittest discover -s loop/tests`）以及该工作项相关的产品门禁（至少 `unittest discover -s tests` 与 `main.py --self-test`），独立记录退出码；只读实现者贴出的日志摘要不构成验证。可在此最低集合之上按风险追加门禁，但不得少于这一集合。
3. **机器可核查的独立性证据**：`state/evidence-index.json` 中 `record_version:"2.0.0"` 的证据行必须同时携带 `implemented_by` 与 `verified_by`；`validate_loop.py` 把"两者不得相同"作为结构化校验规则强制执行，且 `AC-000`（控制面自身的验收）额外要求存在至少一条 `implemented_by != verified_by` 的证据才允许对应工作项进入 `accepted`（见 `_evidence_baseline_errors` 与 `AC-000` 校验段）。字符串不同但实质是同一决策主体的行为，属于违反本节精神，机械校验暂时无法察觉时，复核仍应视为不满足独立性要求并要求补证。
4. **验证者结论必须能脱离实现者的解释单独成立**：验证者不得以实现者对失败原因的自述、猜测或"应该没问题"的推断作为证据来源；只接受规格文本、diff、命令原始输出和产物哈希；`accept` / `changes_requested` / `needs_human` 结论必须写明依据的是哪条原始证据。
5. **人工兜底不可被自动化替代**：无论上述机制如何自动化，触及 `SCOPE_AND_AUTHORITY.md` 中 `HG-*` 人工门禁的事项，验证者的 `accept` 结论不能替代人工批准。

## 8. 每轮必写记录

1. `state/progress.jsonl`：动作、结果、证据、下一步。
2. `state/current.json`：当前阶段、工作项、门禁摘要。
3. `state/evidence-index.json`：新增证据索引。
4. 相关风险、假设、决策或缺陷登记。
5. 如状态改变，重新渲染 `STATUS.md`。

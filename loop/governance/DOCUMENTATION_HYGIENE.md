# 文档卫生 / Documentation Hygiene

本文件是**文档去向与淘汰清理规则**的唯一权威定义。`loop/README.md`"文档卫生"一节只做摘要式引用，不重复独立维护。

## 三个目录的分工

仓库里只有三处放文档，各有明确职责，**不存在第二套权威源**：

| 目录 | 是什么 | 权威性 |
|---|---|---|
| `loop/` | 工程控制面：目标、需求、验收、架构决定（ADR）、风险、质量门、验证证据，以及把控制面建成今天样子的**过程性记录**（`planning/archive/`） | **唯一权威**。任何地方与它冲突，以它为准 |
| `../../docs/` | 教学材料：讲原理、讲取舍、讲踩过的坑，面向想读懂这个项目的人；界面概念稿（`ui-concepts/`）作为设计参考同处一地 | 不是真源。与 `loop/` 冲突时以 `loop/` 为准 |
| `README.md`（仓库根） | 面向使用者与贡献者的入口：怎么跑、怎么打包、目录结构 | 不是真源 |

> **`docs/` 这个名字被复用过一次，读历史记录时注意区分：**
> 早先的 `docs/` 装的是叙事性规划材料（设计规格与实施计划）加界面概念稿。那一版已解散——
> 过程性记录迁入 `loop/planning/archive/`（Loop Engineering 的内容统一收拢在 `loop/`），
> 教学长文与概念稿迁出后一度落在 `knowledge/`，其后按仓库惯例改回 `docs/`。
> 所以**今天的 `docs/` 是教学材料目录，不再是规划材料目录**；`EVD-LOOP-014`/`015` 等历史证据里
> 写的 `knowledge/` 指的就是今天的 `docs/`，那些记录按当时事实留存，不追改。
>
> **界面概念稿不能放进 `loop/`**——`.gitattributes` 对 `loop/**` 强制 `text eol=lf`，
> 二进制 PNG 会被当文本处理而损坏，且控制面摘要与 LF 不变量测试都以「`loop/` 全是文本」为前提。

## 新设计工作去向

- 新的设计说明写入 `loop/planning/archive/specs/<YYYY-MM-DD>-<slug>-design.md`；新的实现计划写入
  `loop/planning/archive/plans/<YYYY-MM-DD>-<slug>.md`，沿用既有命名（日期前缀 + 短横线 slug）。
- 计划执行过程中产出的、需要长期保留的内容（不可妥协原则、架构决定、需求、验收标准、追溯关系、
  验证证据）必须落到 `loop/` 对应文件里；`planning/archive/plans/` 下的计划文件本身是执行记录，
  不作为这些内容的长期第二真源。
- 教学性内容（讲解原理、概念、技巧）写入 `../../docs/`，并挂进 `../../docs/index.html` 的阅读路径，
  不散落在其它地方。

## 淘汰材料的清理

- 一份 `planning/archive/` 文档一旦被 `loop/`（或取代它的新设计文档）取代，且其独有价值已经提炼进
  `loop/` 或已在 `src/` 中实现，就应当删除，不得无限期堆积在当前文档旁边"腐烂"。
- 删除前必须依次确认：
  1. 独有内容已提炼到 `loop/` 的对应文件，或已确认在 `src/` 中实现（不是靠记忆判断，而是实际读过、grep 过）。
  2. 用 `git grep` 排查仓库内（不含本文件与相关计划文件本身）是否还有指向该文件的悬挂引用，并修复真实引用。
  3. 在提交信息和/或就近的索引文档里留下一个 git 历史定位点（基线提交哈希或等效指引），使内容仍可通过
     `git log --all --full-history -- <path>` 或 `git show <commit>:<path>` 找回。
- 删除使用正常的 `git rm` + 提交，不使用 `--no-verify` 或历史重写；因此"删除"不等于"丢失"——仍可从 git 历史完整恢复。
- **保留而非删除的判据**：如果一份文档记录了**被否决的方案及其否决理由**，删掉就再也答不出"当时为什么
  不选另一条路"（ADR 只留结论）。这类过程性记录留在 `planning/archive/`，并在其 README 里写明
  "只回答当初为什么，不回答现在是什么"。
- 本政策的首次落地是 WS-9 文档整理（Plan 5）：15 个 pre-2026-07-11 Tkinter 时代的 `specs`/`plans`
  文档在提炼后被删除，检索方式（含初始基线提交 `61b3cde`）记录在当时的 `docs/README.md` 里，
  该文件本身可由 `git show 5a12997:docs/README.md` 取回。

一、TDD：先写会失败的测试

RED    写一个测试，运行，确认它因为正确的原因失败
GREEN  写最少的代码让它通过
REFACTOR  在保持绿的前提下整理
「确认它因为正确的原因失败」是最容易被跳过、也最关键的一步。 没看过测试变红，你就不知道它到底测没测到东西——很多"测试后补"的用例其实永远是绿的， 把实现删掉它照样通过。

一个真实例子

给门禁运行器加 --strict 参数时，先写的测试是：

self.assertEqual(run_gates.main([]), 0)            # 默认：SKIP 不算失败
self.assertEqual(run_gates.main(["--strict"]), 1)  # strict：SKIP 即失败

运行后它红了，报错是 unrecognized arguments: --strict，同时 stdout 打出：

[G-FAKE     ] SKIP (no_such_module_xyz not installed)
RUN_GATES_OK ran=1 failed=0 skipped=1

这行输出本身就是缺陷的证据：一个根本没跑的门禁，进程却退出 0。 先看到这一幕，再去实现，心里就非常清楚在修什么。

好测试 vs 坏测试

坏好
断言 mock 被调用时传了测试自己传进去的参数断言真实行为：给定输入，输出符合预期
sleep(1) 然后断言注入假时钟 / 等待信号 / 断言可观察状态
测试名叫 test_1测试名说清被保护的性质，如 test_cancelled_snapshot_marks_the_report_cancelled_not_errored
把实现删掉测试照样过删掉实现必红（可以真的试一次，叫变异验证）

二、八道质量门禁

本项目用一个门禁运行器把所有检查串起来，任何一道红就整体失败。

门禁检查什么
G-LOOP控制平面自身一致性：schema 校验、追溯完整、状态文件与工作项状态相符、核心边界、loop 工具测试
G-FORMATruff format --check 全仓
G-LINTruff check 全仓
G-TYPEpyright 静态类型
G-CORE产品测试全绿 + 离线自检；并用 AST 强制领域内核的纯度
G-COVERAGE逐维度断言覆盖率下限（整体语句/分支、核心语句/分支各有阈值）
G-SECURITY导出注入中和等安全用例
G-SURFACE每个声明已交付的能力都必须能从装好的主窗找到对应部件
G-SURFACE 存在的原因值得记住。这个项目发生过两轮「宣称已交付却接不通」： 决策强度切换、证据视图、仓位计算器、横向对比、可信度回测——实现与单测全都齐备， 但相应部件从未被挂进任何页面，用户根本点不到。

单元测试结构上抓不到这类问题：它直接构造部件来测，而恰恰"把部件装进页面"这一步被跳过了。 所以需要一道从装配好的主窗口往下找的门禁。

覆盖率的正确用法

coverage report --fail-under=85 比较的是语句+分支的合并值， 它并不断言你文档里写的那四个阈值中的任何一个。本项目改用自己的检查脚本， 逐维度断言：整体语句 ≥ 90%、整体分支 ≥ 85%、核心语句 ≥ 95%、核心分支 ≥ 90%。

另外：高覆盖率不等于测得好。死代码被它自己的测试覆盖到 100%， 覆盖率报告一片绿——本项目就删掉过两个这样的模块。

三、loop 控制平面：让文档不能说谎

loop/ 目录是这个项目最独特的部分：它把「当前状态」做成机器可校验的数据， 而不是一堆会过期的散文。

目录内容
product/需求（REQ-*）、验收标准（AC-*）、能力面、设计 token
decisions/架构决策记录（ADR），16 份，每份含背景/决策/后果
architecture/模块边界、数据流、并发、安全威胁模型、打包……
quality/门禁定义、测试目录、追溯矩阵、发布就绪清单
planning/工作项（WI-*）、里程碑、依赖图
state/当前状态、度量、证据索引（机器渲染，不手写）
evidence/每条结论背后的实跑证据文件

摘要锚定（digest anchoring）

control_plane_digest() = sha256(loop/ 下所有受管文件的字节)

这个摘要被记录在「基线证据」里。任何人改动 loop/ 的任何一个字节，摘要就变， G-LOOP 立刻失败——除非同时走再基线协议：写一份说明改了什么、为什么改的证据文件， 并把新摘要登记进去。

这条机制的价值在于：它让「悄悄改文档」变得不可能。 你可以改，但必须留下一份说明。工程治理最难的不是写规则，而是让规则无法被绕过。

计数锚点：防止数字悄悄烂掉

状态文件里记着「测试总数」。这个数字会随着开发不断变化，如果没人管，它就会慢慢和现实脱节—— 本项目里它曾经长期停在 814，而真实套件早已远超那个数。 

def test_metrics_product_test_count_is_anchored_to_the_real_suite():
    suite = unittest.defaultTestLoader.discover("tests")
    assert metrics["tests"]["methods"] == count(suite)   # 记录必须跟着真实套件走

加上这条测试后，每次新增测试都会让它变红，逼你顺手把记录改对。无锚点的数字必然烂掉。

四、CI 的两个真实坑

坑一：门禁"跳过"却算成功

门禁运行器为了在新检出的机器上可用，把「工具没装」降级成 SKIP 而不是崩溃。 这在本地是便利，在 CI 里是毫无根据的绿——一个装不上的 pyright 会让类型门禁悄悄消失， 流水线照样通过。 

CI 必须用：run_gates.py --strict     # SKIP 计为失败

坑二：换行符让摘要在 CI 上必然不匹配

摘要按字节计算。.gitattributes 声明 loop/** text eol=lf， 所以 git 存 LF、CI 检出也是 LF。但如果本地的写文件代码用文本模式， Windows 上会写出 CRLF——于是「本地算出的摘要」与「CI 检出后算出的摘要」永远不同， 第一次真实 CI 运行就会因为换行符而失败，且原因与代码质量毫无关系。

解法：写文件时显式 newline="\n"，并加一条测试断言 loop/ 下任何文件都不含 CRLF。

CI 里的其它要点

配置为什么
timeout-minutes不设的话，一个卡住的任务会烧到 6 小时默认上限
concurrency + cancel-in-progress新推送让在途运行作废，不用两个 runner 抢答同一个问题
permissions: contents: read最小权限：这个流水线只需要读仓库
QT_QPA_PLATFORM=offscreenQt 测试要构造真实 QWidget，offscreen 是唯一不需要显示器的平台插件

五、打包与交付

onedir 而不是 onefile

形态热启动LGPL 重链接义务
onefile（单个 exe）2.903 秒（每次启动重新解压约 100 MB）做不到
onedir（应用目录）0.685 秒可以
两条独立理由都指向 onedir： ① 单文件热启动超出 2.5 秒的性能预算； ② PySide6 以 LGPL-3.0 分发，其第 4(d) 条要求用户能用自己编译的 Qt 重新链接—— 只有当 Qt 动态库是可替换的独立文件时这条义务才履行得了。

许可证是真实的工程约束，不是法务的事后审批。

为什么用 PySide6-Essentials 而不是 PySide6

PySide6（元包）= Essentials + Addons = 634.1 MB
PySide6-Essentials              = 202.2 MB
其中 Qt6WebEngineCore.dll 一个文件就 195.3 MB —— 而这个产品根本不用浏览器内核

发布元数据

产物作用
SBOM.json（CycloneDX 1.5）软件物料清单：交付物里到底有哪些组件、什么许可证
THIRD_PARTY_NOTICES.md第三方许可通知

交付物自检

dist\股市锦囊\股市锦囊.exe --self-test
→ SELF_TEST_OK ... checks=8/8   退出码 0

打包成功不等于能跑。自检用内置样例数据把个股分析、五档决策、仓位、回测、持久化、 横向对比、条件预警、全市场选股整条链路跑一遍，不联网、不开窗。这是发布前的可复现合同。

六、可复现构建

[project].dependencies      PySide6-Essentials==6.11.1   ← 运行期唯一第三方依赖
[dependency-groups].build   pyinstaller==6.21.0          ← 构建期唯一依赖，钉死版本
[dependency-groups].dev     ruff / pyright / pytest / coverage / pre-commit
构建依赖必须钉死版本：交付物的可复现性取决于它。浮动版本会让「同一个提交构建出不同产物」成为可能， 而那时你连 bug 是自己引入的还是工具链变的都分不清。

本篇要点回顾

  • TDD 的关键是亲眼看到红，且红的原因正确。
  • 门禁要覆盖到装配层——单元测试抓不到「部件没被挂进页面」。
  • 覆盖率要逐维度断言；高覆盖率不等于测得好，死代码也能 100% 覆盖。
  • 让文档不能说谎的办法是摘要锚定 + 计数锚点：无锚点的数字必然烂掉。
  • CI 里 SKIP 必须算失败；换行符能让字节级校验在 CI 上必然失败。
  • 打包选型受性能预算与许可证义务双重约束；构建依赖钉死版本。

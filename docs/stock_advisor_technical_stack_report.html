1. 项目总览

股市锦囊是一个只用 Python 标准库构建的 Windows 桌面程序，最终打包为单文件 EXE（股市锦囊.exe），放在任意位置都能直接运行。它提供两种核心能力：个股分析（输入一个或多个 A 股代码，基于实时行情 + 历史日线，用可解释的多因子模型给出当日「买入/持有/卖出」倾向、理由、风险与保守投入参考）与全市场选股（从六种策略预设中选择、微调关键参数，从当前全市场实时行情中按证券特征自动挑选股票，并对入选股做与个股分析一致的深度判断）。贯穿两页的核心是五档决策强度（稳健·稳进·标准·积极·激进）：客观测量不变，只切换决策策略，点选档位即时重算、不重新联网。

重要边界：模型仅供研究和辅助决策，不构成投资建议；交易前请自行核验行情、公告和风险。程序使用规则型技术分析和行情数据生成辅助判断，不能替代投资者自己的决策；报告中的算法说明用于教学，不能被理解为盈利保证。（本段核心措辞与 dist/使用说明.html 页脚一致，权威来源见 theme.DISCLAIMER / models.CORE_DISCLAIMER。）

从用户视角看程序做了什么

  1. 用户输入股票代码，例如 600519、000001、300750；或切到「全市场选股」选项卡挑一个策略预设。
  2. 程序自动识别交易所前缀，整理为 SH.600519、SZ.000001、BJ.xxxxxx 这种展示格式；全市场选股页则直接使用行情接口自带的权威市场号，不做前缀猜测。
  3. 后台请求实时行情和历史日线（或全市场快照）。主行情源失败时自动切换备用行情源。
  4. 客观测量层计算均线、趋势、买卖力量、成交配合、波动、支撑压力等 8 个因子和风控扣分，得到与决策档位无关的「测量」；决策层按当前选中的决策强度档位，把测量结果翻译成买入/持有/卖出、建议仓位与止损止盈。
  5. 界面用分段选项卡、颜色、决策强度光谱、专业 K 线图、仓位/风控计算器和解释文本展示结果；自选股/持仓、本金、档位、选股预设与预警规则会跨会话自动保存。

标准库优先的工程取舍

项目没有引入 pandas、numpy、requests、matplotlib、PyQt 等常见第三方库，运行期完全用标准库完成主要工作（构建期唯一依赖 PyInstaller）。这会让代码更“手写”，但也带来三个直接收益：

  • 轻便：打包体积更小，依赖冲突更少。
  • 可解释：算法和数据结构都在源码中，学习者能直接看到每一步。
  • 部署简单：用户拿到一个 EXE 就能运行，不需要安装 Python 和依赖包。

3. 架构与数据流

程序采用「输入解析 → 行情获取 → 客观测量 → 按档决策 → 结果展示 → 导出/持久化」的分层结构。全市场选股复用同一条测量/决策管线，只是入口换成批量快照 + 过滤排序。每层职责相对清晰，便于测试和替换。

输入层用户输入股票代码或选股预设，整理、去重、推断交易所。
数据层请求实时行情、历史日线或全市场快照，多源回退。
测量层engine.measure() 算出与档位无关的客观 Measurement。
决策层policy.decide() 按当前决策强度档位算出买/持/卖、仓位与止损止盈。
展示/交付层Tkinter 表格、K 线/光谱 Canvas、CSV/剪贴板、跨会话持久化、PyInstaller 单文件 EXE。

关键思想

  • 测量与决策分离：engine.measure() 产出客观 Measurement，与决策档位无关；policy.decide(m, level) 按 5 档决策强度翻译为买/持/卖、仓位与止损止盈；engine.analyze_stock(..., level) 是二者的薄包装，默认 L3「标准」复现历史上「单一 ±25 阈值」的行为。切换档位只对已缓存的 Measurement 重新 decide()，不重新联网。
  • 业务模型与 UI 分离：models.py、engine.py、policy.py、backtest.py、chart.py、screener.py、presets.py、compare.py、alerts.py、input_validate.py、layout.py、formatting.py 均不依赖 Tkinter，可独立单测。
  • 数据源与分析流程分离：workflow.py 通过 MarketDataProvider / ScreeningProvider 两个 Protocol 调用数据源，测试中可以替换为 FakeProvider；分析结果连同底层 Measurement 一起回传，供界面改档即时重判。
  • GUI 主线程不做耗时任务：个股分析、全市场选股、条件预警轮询、个股资金流查询这四类后台任务都在各自线程执行，结果经 queue.Queue 回传，主线程统一用 root.after() 定时轮询消费，避免窗口卡死。
  • 异常分级处理：实时行情失败会导致该股票失败；历史行情失败会降级为保守判断并提示用户；资金流失败只影响资金流面板本身；配置文件读写失败一律回退默认值，绝不崩溃。

3.1 个股分析管线

用户输入股票代码
  -> symbols.parse_user_symbols()
  -> EastmoneyProvider.fetch_quote() / fetch_history()（多源回退）
  -> engine.measure()                       得到与档位无关的 Measurement
  -> policy.decide(measurement, level)      按当前决策强度档位得到 Decision
  -> engine.build_analysis_result()         组装 AnalysisResult
  -> 分段选项卡表格 + K 线/光谱 Canvas + 详情文字 + CSV/剪贴板

（切换决策强度档位时：直接对已缓存的 measurement 重新 decide()，不重新请求网络）

3.2 全市场选股管线

选择策略预设 + 微调关键参数
  -> presets.apply_tunables()               得到 FilterCriteria
  -> EastmoneyProvider.fetch_market_snapshot()  全市场快照（clist 接口，多页拉取）
  -> screener.apply_filters() + screener.rank()
  -> workflow.screen_and_recommend()：对入选股逐个复用「个股分析管线」做深度判断
  -> Recommendation 列表 -> 表格 + 详情（与个股分析共用同一套展示组件）

领域模型的意义

程序没有直接在各处传递字典，而是把数据拆成有名字的结构。例如 Quote 表示实时行情，DailyBar 表示一根日 K 线，Measurement 表示与决策档位无关的客观测量，Decision 表示某一档位下的决策结果。这样做有几个好处：

  • 字段含义清楚，例如 previous_close 明确是昨收价，不会和开盘价混淆。
  • 类型提示能帮助开发者发现传参错误。
  • 测试可以直接构造模型对象，不需要模拟完整网络响应。
  • 测量与决策拆成两个不可变对象，使“改档不改测量”这一行为在类型层面就能表达清楚，而不用靠注释约定。

5. 行情数据层

数据层位于 data_provider.py，是项目中唯一做网络请求的模块，负责把外部行情接口转换为内部统一的 Quote、DailyBar、MarketSnapshot、FundFlow。这是程序可靠性的关键。

5.1 股票代码和市场编码

A 股代码本身只有 6 位数字，但不同数据接口需要不同的市场前缀。用户手工输入的场景由 symbols.py 按代码前缀推断交易所；全市场快照场景则不靠推断——直接使用东方财富接口返回的权威市场号字段 f13（symbols.symbol_from_market()），因为批量场景下前缀猜测更容易出错。

全市场快照中的每一行权威市场号：f13（1=沪，0=深/北），不猜前缀由 symbol_from_market() 构造{market}.{code}

5.2 实时行情获取

实时行情优先使用东方财富接口；如果失败，回退到新浪行情接口（gb18030 编码）。解析时会把接口字段映射到统一的 Quote：

  • last：最新价；open：开盘价；high / low：当日最高和最低；previous_close：昨收价。
  • volume / amount：成交量和成交额；turnover_rate：换手率；change_pct：涨跌幅。

东方财富部分价格字段是放大后的整数，代码用 _scaled_price() 除以 100 还原；百分比字段用 _scaled_percent() 做同类处理。

5.3 历史日线多源回退

历史数据是指标计算的基础。项目按以下顺序获取日线：

  1. 东方财富历史 K 线接口。
  2. 新浪日线接口。
  3. 腾讯前复权日线接口。
  4. 腾讯普通日线接口。

只要任意一个源返回有效数据，程序就继续完整分析。如果所有历史源失败，workflow.py 会降级为仅用实时行情做保守判断，并在风险列表中加入用户友好的提示。

5.4 编码、JSON 和异常处理

不同源返回编码不同。新浪接口常用 gb18030，其他接口多为 UTF-8。程序在请求时允许传入编码参数，并使用 errors="replace" 避免个别字符导致整体解码失败。

异常处理覆盖了 URLError、TimeoutError、RemoteDisconnected、ConnectionError 和 OSError。这对应现实中常见的网络不通、远端断开、连接重置、DNS 或 TLS 问题。

5.5 全市场快照（选股数据源）

fetch_market_snapshot() 分页拉取东方财富 clist 接口，逐页解析为 MarketSnapshot 列表，供全市场选股使用。每条快照包含价格、涨跌幅、成交量/额、振幅、换手率、量比、总市值/流通市值、涨速、PE/PB、60 日涨幅、年初至今涨幅等约 18 个字段；缺失字段一律记 None，无效价格行直接跳过。是否为 ST/退市风险股由名称含 ST/*ST/退 判断（MarketSnapshot.is_st）。

5.6 个股资金流（按需查询）

fetch_fund_flow() 请求 stock/fflow/kline/get 接口，解析今日主力净流入与近 5 日累计（FundFlow）。该接口偶发被限流或拒连，因此只做按需、独立的查询——用户在结果表选中一只已分析的股票后点「资金流」才会触发，走独立的后台线程 + 队列，取不到时提示稍后重试，绝不影响个股分析或全市场选股的核心流程。

6. 策略算法与五档决策强度

项目不是机器学习模型，而是规则型策略引擎，并且明确拆成两层：测量层（engine.measure()，只看行情本身，与用户选了哪个决策强度档位无关）和决策层（policy.decide()，按用户当前选中的档位把测量结果翻译成买/持/卖、仓位与止损止盈）。同一次测量，五个档位会给出五个可能不同的结论——这正是「决策强度光谱」的由来。

6.1 输入数据与客观测量层

engine.measure(quote, history) 接收两个核心输入：

  • Quote：当日实时行情，提供最新价、涨跌幅、当日高低价、成交量等。
  • list[DailyBar]：历史日线序列，提供历史收盘价、成交量、最高价、最低价等。

如果历史收盘价最后一项和实时最新价差异明显，代码会把实时最新价追加到收盘价序列中，使指标尽量反映当日状态。measure() 的输出是一个不可变的 Measurement，其中的分数、置信度都与决策强度档位无关——切换档位不会重新计算指标，只会重新决策。

6.3 因子评分体系

程序将指标转化为 8 个 FactorScore，每个因子包含名称、分数、最大绝对分、结论和说明；组装展示结果时再加入「风控扣分」作为第 9 项。主要因子包括：

均线结构 趋势质量 动量指标 量能确认 日内位置 布林位置 支撑压力 波动风险 风控扣分

例如，价格站上 5 日和 20 日平均线且短中期结构共振，会给“均线结构”加分；若价格跌破短中期平均线，则会扣分。成交量放大并伴随上涨，会给“量能确认”加分；放量下跌会扣分。详情面板里每一条因子说明都按分数正负着色（正分红、负分绿），实现见 view_format._score_color()，与买卖同一套配色规则、同一处代码来源。

6.4 客观综合分与置信度

8 个因子分数求和得到 base_factor_sum；加上风控扣分 risk_penalty（≤0）得到 objective_score，并限制在 -100 到 100 之间。历史样本少于 30 个交易日时，objective_score 会先乘以 0.75 再四舍五入下调，并加入风险提示。confidence（置信度/把握程度）由综合分强弱、历史样本数量、关键指标可用性和波动风险共同影响，不是概率预测，而是“当前证据一致性”的量化表达。

教学提醒：规则型评分引擎的优势是透明、可解释；劣势是不能自动学习市场状态变化。使用这类系统时，应关注规则是否合理、数据是否可靠、风险边界是否明确。

6.5 五档决策强度：从测量到决策

旧版本只有一种决策口径：综合分 ≥25 买入、≤-25 卖出、仓位统一封顶 80%。当前实现是五档决策强度（STANDARD_LEVEL = 3 为默认档，即「标准」），每档各自的买卖线、风控扣分权重、置信度门槛、单笔风险预算、仓位上限、目标盈亏比都不同，定义在 policy.LEVELS：

档位名称买入线
t_buy		卖出线
t_sell		风控扣分权重
risk_weight		置信度门槛
confidence_gate		单笔风险预算
risk_budget		仓位上限
position_cap		目标盈亏比
reward_risk
L1稳健≥ 40≤ -151.6700.5%30%2.5
L2稳进≥ 33≤ -191.3600.75%45%2.2
L3标准（默认）≥ 25≤ -251.0不设门槛1%60%2.0
L4积极≥ 18≤ -330.8不设门槛1.5%75%1.7
L5激进≥ 12≤ -420.6不设门槛2%90%1.5

从表里的真实数字可以直接读出规律：

  • 买入线 t_buy 逐档走低（40 → 33 → 25 → 18 → 12）：越激进，越容易在信号还不算很强时就给出买入。
  • 卖出线 t_sell 逐档走低（-15 → -19 → -25 → -33 → -42，绝对值增大）：越保守，越容易在只是小幅走弱时就触发卖出（快出、优先护本）；越激进，越能容忍更深的浮亏才卖出（愿意扛单）。
  • 风控扣分权重 risk_weight 逐档走低（1.6 → 0.6）：同样的风控扣分，在保守档会被放大 1.6 倍拉低决策分，在激进档只打 0.6 折。
  • 置信度门槛只在 L1/L2 生效：即使分数已达买入线，L1 要求把握程度 ≥70、L2 要求 ≥60 才真正给出买入，否则降级为观望；L3~L5 不设这道门槛。
  • 单笔风险预算与仓位上限同步走高（0.5%→2%，30%→90%）：越激进，允许单笔承受的风险和总仓位占比都越大。
  • 目标盈亏比逐档走低（2.5 → 1.5）：保守档只在“止盈空间明显大于止损距离”时才值得参与，激进档对盈亏比的要求更宽松。

决策分的计算：policy_score()

score = base_factor_sum + risk_penalty * risk_weight(该档)
若历史样本 < 30 天：score *= 0.75
score = clamp(score, -100, 100)（四舍五入取整）

L3「标准」档的 risk_weight = 1.0，且不设小样本以外的额外调整，所以 policy_score(m, 3) 恒等于 measure() 算出的 objective_score——这正是 L3 复现「历史单一阈值模型」的原因，也是为什么本报告仍然用「≥25 买入 / ≤-25 卖出」举例：那只是五档里 L3 这一档的数字，不再是全部。

动作判定：_action()

以 L3 标准档为例（t_buy=25，t_sell=-25，不设置信度门槛）：

决策分范围（L3）动作解释
policy_score >= 25买入 / 加仓多项迹象偏积极，但仍要结合风险分批参与。
policy_score <= -25卖出 / 减仓走弱或风险迹象更明显，优先控制回撤。
-25 < policy_score < 25继续持有 / 观望信号分歧，等待方向更清楚。

其余四档把 25 / -25 换成各自的 t_buy / t_sell（见上表）即可，逻辑完全一致；L1/L2 额外要求把握程度过置信度门槛才放行买入。

6.6 仓位与风控计算器

size_fraction() 决定「建议投入比例」（占本金，上限为该档的 position_cap）：

stop_pct  = clamp(2%, 12%, 1.8 × ATR百分比)          止损距离，缺 ATR 时退化用常态波动或默认3%
strength  = clamp(0.4, 1.0, |policy_score| / 55)      分数强度
conf      = clamp(0.5, 1.0, confidence / 100)         把握程度
frac      = clamp(0, position_cap, (risk_budget / stop_pct) × strength × conf)

position_plan() 结合用户填写的本金，把比例落到绝对股数（按 100 股/手取整）、止损价、止盈价、盈亏比与最大亏损额：

举例（L3 标准档）：最新价 20 元，ATR 2.5%，把握程度 80，决策分 45，本金 10 万元。
stop_pct = clamp(2,12, 1.8×2.5) = 4.5% → 止损价 19.10 元；目标盈亏比 2.0 → 止盈价 21.80 元。
strength = 45/55 ≈ 0.818，conf = 0.8，frac = (1%/4.5%) × 0.818 × 0.8 ≈ 14.5%（未超 60% 上限）。
股数 = ⌊100000 × 14.5% / 20 ÷ 100⌋ × 100 = 700 股（7 手），成本 14000 元，最大亏损 ≈ 630 元（占本金约 0.63%）。

建议投入比例是保守参考，不是必须执行的仓位；风险越高、把握越低、样本越少，比例自动越低。这体现了一个基本风控原则：即使判断偏积极，也不会无脑建议满仓，而是把仓位上限也纳入了决策强度档位本身。

6.7 决策强度光谱与翻转提示

spectrum(m, current_level) 用同一个 Measurement 分别跑五档 decide()，返回可供「决策强度光谱」横向渲染的五个单元（含当前档高亮）；flip_hint() 用一句话点出该股在哪一档发生买/卖翻转，例如“需到「积极」及以上才建议买入；更保守则观望”。这让用户一眼看出一只股票是“各档都买”的强信号，还是“只有放宽风险容忍度才买”的边缘信号。

6.8 可信度回测

backtest_signals(history, level, horizon=5, warmup=30, cost_pct=0.13) 对同一只股票的历史数据做逐日、无未来泄漏的信号回放：第 t 日的信号只用 history[:t+1] 计算（measure() + 该档 decide()），未来 horizon 个交易日的收益只用于事后度量、不作为信号输入。按买入/卖出/持有分组统计样本数、胜率（卖出信号“对”定义为之后下跌）、平均收益，并与同期买入持有基线对比。样本有限、计入单边成本，不预示未来——这是回测模块自身在结果文案里就会声明的边界。

界面层位于 app.py，使用 Tkinter 构建。Tkinter 是 Python 标准库自带的桌面 GUI 工具包，底层依赖 Tcl/Tk。它适合构建轻量级、无需额外安装依赖的 Windows 桌面工具。

7.1 配色约定（本次重点修正）

程序统一采用 A 股本土配色习惯：红 = 涨 / 买入 / 积极 / 正分；绿 = 跌 / 卖出 / 谨慎 / 负分。权威定义在 theme.py：

买入 / 加仓（红字 + 淡红底） 卖出 / 减仓（绿字 + 淡绿底） 继续持有 / 观望（中性灰 + 淡灰底）

容易搞混的地方：国际软件的通用习惯是“红色=危险/警告”（本报告的风险提示框也用了近似的红色边框，语义是“重要/危险”，跟本节讨论的涨跌颜色是两套独立语境）；但 A 股行情软件里红/绿的含义相反于西方股市（美股通常红跌绿涨）。这份报告此前的版本就是把“危险色该谨慎卖出、安全色才可以买入”这套直觉误套到了 A 股配色上——买入配了偏安全感的颜色、卖出配了偏警示感的颜色，正好和 A 股习惯相反，而且给买入文字包了一个按颜色字面命名的 CSS 工具类（类名本身就是颜色单词）。按颜色命名的工具类，在语义相反的场景下极易被写反。这也是本次修正把 CSS 类名改成 .pos/.neg（按“积极/消极”语义命名而非按颜色命名）的原因，用 theme.py 的 POS_COLOR/NEG_COLOR 命名方式对齐，从命名上直接消除再次讲反的空间。

7.4 后台线程和队列

GUI 程序最重要的工程原则之一是：不要在主线程做耗时任务。主线程负责重绘窗口和响应用户事件，如果它去等待网络请求，窗口就会卡住。项目对个股分析、全市场选股、条件预警轮询、资金流查询这四类耗时操作，统一采用如下模式：

触发操作（点击按钮 / 定时轮询）
  -> 创建/复用后台线程
  -> 后台线程请求行情并调用 measure()/decide()
  -> 通过 queue.put() 投递结果
  -> 主线程 root.after(间隔, _poll_xxx) 定时取结果并更新 UI

这种模式叫“生产者消费者”。后台线程是生产者，负责生产结果；GUI 主线程是消费者，负责安全更新控件——四类任务各自有独立的队列和轮询方法，互不阻塞。

7.5 K 线与光谱可视化

程序没有使用 matplotlib，而是用 Canvas 直接绘图，配合 chart.py 的纯函数几何映射（价格/成交量转像素坐标、最近点命中）：

  • K 线：蜡烛图 + MA5/10/20 均线 + 成交量副图，鼠标移动时显示十字光标与当根 OHLC。
  • 决策强度光谱：同一只股票五档结论横向对照。
  • 动作徽章、综合判断/投入比例/把握程度指标条、近期价格走势小图、判断拆解因子条（正负分以方向和颜色区分）。

这种方式轻量、无依赖，比早期版本的简易因子条更进一步做到了专业 K 线的观感，但仍不是通用图表组件，交互能力（缩放、多周期切换等）有限。

为什么测试里要用 FakeProvider 和 mock

真实行情接口会受网络、时间、远端服务影响。测试如果依赖真实网络，就会不稳定。项目在 test_workflow.py 中使用 FakeProvider，在 test_provider.py 中使用 patch 模拟 urlopen，这样能确定性地测试失败和回退场景；配置持久化测试通过环境变量 STOCK_ADVISOR_CONFIG 指向临时文件，绝不写真实 %APPDATA%。

provider = EastmoneyProvider(timeout=0.1, max_retries=1)
with patch.object(provider, "_request", fake_request):
    rows = provider.fetch_history(normalize_symbol("600519"), limit=1)

9. 打包发布

打包由仓库根目录的 build_exe.py 完成，构建依赖写在 requirements-build.txt，当前只有 pyinstaller>=6.15。运行时程序本身只依赖标准库。也可以直接用一键脚本：

build.bat            # Windows（cmd / PowerShell）
./build.sh           # Git Bash / WSL
# 或手动：
python -m pip install -r requirements-build.txt
python build_exe.py

PyInstaller 的角色

PyInstaller 会分析入口脚本依赖，把 Python 解释器、字节码、标准库、Tk 运行资源和项目源码打包成可执行文件。项目使用了几个关键参数：

参数作用
--onefile生成单个 EXE，便于交付。
--windowed启动时不弹出控制台窗口，适合 GUI 程序。
--disable-windowed-traceback窗口模式下未捕获异常不弹出系统级 traceback 对话框。
--icon / --add-data指定应用图标，并把图标文件一并打进 assets/ 目录供运行时读取。
--clean清理 PyInstaller 缓存，降低旧构建影响。
--optimize 2启用字节码优化。
--exclude-module unittest/pydoc/doctest/pdb/idlelib排除运行时不需要的模块，减少体积。
--paths src让 PyInstaller 能找到 stock_advisor 包。
--distpath / --workpath / --specpath全部指向 build/ 内部，PyInstaller 自身产物不会污染 dist/。

构建目录约定与安全设计

build/ 只放构建中间产物（含 PyInstaller 原始输出）；dist/ 只放最终交付物。build_exe.py 在删除 build//dist/ 前会检查路径是否位于项目目录内，避免误删项目外路径。构建完成后：

  • PyInstaller 产物从 build/pyinstaller/AStockIntradayAdvisor.exe 复制为最终交付名 dist/股市锦囊.exe。
  • manual.build_manual_html() 动态生成 dist/使用说明.html，写入 dist/。

自检模式 --self-test（dist\股市锦囊.exe --self-test）用于验证 EXE 的基础可执行性：它构造离线样例，跑一遍个股分析、五档决策、仓位、回测、持久化、横向对比、条件预警和全市场选股全链路，成功时打印 SELF_TEST_OK ... 并以退出码 0 结束，不依赖网络和窗口交互。

为什么 dist/使用说明.html 不会像本报告曾经那样“讲反”：用户手册由 manual.build_manual_html() 在每次打包时，直接从 app.py/theme.py/presets.py/screener.py 等运行代码里的真实常量和文案动态拼出，不存在人工誊抄环节，源码一变手册自动跟着变。而本技术报告（docs/stock_advisor_technical_stack_report.html）是人工撰写的静态文档，与源码没有强制同步机制，需要在每次架构或配色变更后人工复核更新——这正是它此前会与实现脱节甚至讲反的根本原因。

10. 防御性设计与边界条件

这个项目有不少防御性逻辑，目的不是让程序“永远不失败”，而是让失败可控、可解释、不影响其他股票或其它功能。

风险点处理方式文件位置
用户输入格式混乱用正则拆分逗号、空格、换行、中英文分号；自动推断交易所；去重；限制最多 30 只。symbols.py、input_validate.py、app.py
行情接口断开设置超时、重试、请求头；实时行情和历史行情均有备用源。data_provider.py
返回数据缺字段解析函数跳过无效 K 线/快照行，安全转换数字，必要字段无效时抛出业务异常。data_provider.py
历史数据拿不到降级为实时行情保守判断，给用户友好提示，不暴露底层连接错误。workflow.py
样本不足指标返回 None，客观分按 0.75 折降权，风险列表提示样本不足。engine.py
选股参数上下限交叉apply_tunables() 对成对边界（如涨跌幅下限/上限、换手率下限/上限）做协同校验，交叉时抛出可展示的 ValueError，而不是静默返回“无结果”。presets.py
配置文件损坏/不可写读取失败一律回退默认 AppConfig；写入用临时文件 + os.replace 原子替换，测试用环境变量隔离，绝不写真实 %APPDATA%。store.py
资金流接口偶发限流按需查询、独立线程 + 队列，取不到只提示稍后重试，不影响个股分析/选股主流程。data_provider.py、app.py
条件预警重复提醒边沿触发（条件由不满足变为满足才提醒），回落后才能再次触发，避免持续越线时反复告警。alerts.py
GUI 卡死个股分析、全市场选股、预警轮询、资金流查询均在后台线程执行，主线程只消费队列并刷新界面。app.py
高 DPI 显示器界面模糊/错位启动时请求系统按原生 DPI 渲染（SetProcessDpiAwareness/SetProcessDPIAware）。main.py
导出中文乱码CSV 使用 UTF-8 BOM，便于 Excel 打开。view_format.py
误删构建外文件删除 build//dist/ 前校验路径必须在项目内。build_exe.py

当前系统的限制

  • 策略是规则型 + 参数化的五档决策强度，不是机器学习模型，不会从历史回测中自动学习或调整因子权重。
  • 公开行情接口没有稳定性承诺，未来字段或访问策略可能变化；资金流接口尤其容易被限流。
  • 持久化仅保存在本机 %APPDATA%，没有云端/多设备同步。
  • 没有接入账户、交易、下单功能，也不应承担自动交易职责。
  • K 线目前只做日线，没有分时图、集合竞价等更细粒度的图表。
  • 可信度回测只针对单只股票的历史信号复盘，不汇总到预设/策略维度的历史命中率。

11. 学习路线与后续方向

如果以这个项目作为教学案例，可以按以下顺序学习：

  1. Python 基础：函数、类、模块、异常、文件路径、列表和字典。
  2. 类型和数据建模：dataclass、Protocol、类型提示、不可变数据对象。
  3. 输入验证：正则表达式、错误消息、边界限制。
  4. HTTP 和数据解析：请求头、超时、编码、JSON、接口字段映射，含全市场快照与资金流。
  5. 技术指标：均线、EMA、MACD、RSI、布林、ATR、回撤和成交量比。
  6. 规则型策略：测量与决策分离、五档决策强度、仓位与止损止盈计算。
  7. 选股：过滤条件、目标导向打分排序、预设与可调参数的交叉边界校验。
  8. 回测方法论：无未来泄漏的历史信号逐日复盘。
  9. Tkinter GUI：自绘选项卡、Canvas 绘图（K 线/光谱）、事件、表格、线程队列。
  10. 持久化与工作台：配置原子写、自选/持仓、横向对比、条件预警的边沿触发。
  11. 测试：用 unittest 覆盖纯函数、异常路径、模拟网络、headless GUI 测试。
  12. 打包：理解 PyInstaller 如何分析依赖、生成 EXE，以及说明书如何与源码同源生成。
实践建议：先从 models.py 读起，再读 engine.py 的客观测量与 policy.py 的五档决策，然后是 screener.py/presets.py 的选股链路，最后读 app.py。这样能先掌握数据和算法，再理解界面如何调用它们。

可以继续探索的方向（均为尚未实现，非本报告此前误列的那些）

  • 把资金流、ROE 等基本面特征纳入选股筛选与个股评分核心逻辑（目前资金流只是按需查询，不进入综合分）。
  • 让回测结果反过来指导因子权重或档位参数调优（目前回测只读，不闭环调参）。
  • 配置的云端/多设备同步（目前只保存在本机 %APPDATA%）。
  • 分时图、集合竞价等更多图表维度（目前 K 线只做日线）。
  • 把「可信度回测」从单只股票汇总到预设/策略维度的历史命中率统计。

本报告随源码维护，用于教学、代码理解和维护交接；如与运行中的程序出现不一致，以源码（尤其是 theme.py、policy.py）为准。
